# Merchant Open API integration

<!-- Generated by scripts/gen-skill.py from protocol/data/*.json. Do not edit by hand. -->

**Do not hand-roll the signature.** Requests are authenticated with Ed25519 + RFC 9421
HTTP Message Signatures, and write requests also carry an X25519 sealed-box encrypted
body; a home-grown implementation almost always ends in `401`. Use the official SDK
(go / java / js / php / python share one interface). Before sending, the SDK validates
the request locally, so "method code not available for this currency" and "required
field is empty" are caught in-process instead of coming back as a gateway `400`.

**Read <references/methods.md> before writing a single line of payment or payout code.**
Required fields are conditional: within one currency, different method codes require
different fields, and filling them from memory gets the request rejected by the gateway.

## Configuration: six values, all required

The same six values under each language's own names. Using another language's name
fails at client construction.

| Purpose | Go `Config` | JS option / PHP key | Python kwarg | Java builder |
|---|---|---|---|---|
| API base URL, **must be https**, scheme and host only | `BaseURL` | `baseUrl` | `base_url` | `baseUrl(...)` |
| Merchant access key | `AccessKey` | `accessKey` | `access_key` | `accessKey(...)` |
| Merchant Ed25519 private key, base64 (32-byte seed or 64-byte full key) | `MerchantPrivateKeyBase64` | `merchantPrivateKeyBase64` | `merchant_private_key_base64` | `merchantPrivateKeyBase64(...)` |
| ID of the platform body-encryption key | `PlatformBodyKeyID` | `platformBodyKeyId` | `platform_body_key_id` | `platformBodyKeyId(...)` |
| Platform body-encryption public key, X25519, base64 | `PlatformBodyPublicKeyBase64` | `platformBodyPublicKeyBase64` | `platform_body_public_key_base64` | `platformBodyPublicKeyBase64(...)` |
| Platform webhook signing public keys, `keyId -> base64` | `PlatformWebhookPublicKeys` | `platformWebhookPublicKeys` | `platform_webhook_public_keys` | `platformWebhookPublicKeys(...)` |

**The webhook public keys are checked strictly**: they must be present even if you never
verify webhooks, otherwise constructing the client fails and no request can be sent.

**Build the client once and share it.** A constructed client is read-only and safe to
share across goroutines or threads; rebuilding it per call re-parses the private key for
nothing. Build a second one only for a different set of merchant credentials.

## Key rules

- **For the two checkout POSTs, `status` decides success, not the HTTP code.**
  `SubmitPaymentTradeNo` and `AddPaymentExtraInfo` return `HTTP 200` with envelope
  `code: 200` even when rejected; the outcome is in `data.status`: `1` accepted,
  `0` rejected (`message` says why).
  ```jsonc
  { "code": 200, "msg": "OK", "data": { "status": 0, "message": "OrderNotFound" } }
  ```
  A caller that only checks for an error reads a rejection as success. This is the most
  common integration mistake with this API. Check `status` every time; the Go result
  types expose `Ok()`. Field semantics per checkout endpoint are in
  <references/endpoints.md>.

- **Amounts are always decimal strings** (`amount`, `paidAmount`, balances, fees, FX
  rates, e.g. `"100.50"`), never JSON numbers. The SDK passes them through as strings;
  parsing them as floats loses precision.

- **Write calls are not retried automatically, and `merchantOrderNo` is the only
  deduplication key.** A deliberate retry resends the **same `merchantOrderNo` with the
  same parameters**; the platform then returns the existing order or
  `IDEMPOTENCY_CONFLICT` instead of creating a second one. The `Idempotency-Key` header
  is for request tracing and takes a fresh value on every request: reusing it does not
  protect against duplicates, and changing it does not create one. What creates a second
  order is resending under a new `merchantOrderNo`.

- **Every webhook delivery is signed afresh.** Verify it with the SDK's `VerifyWebhook` /
  `ParsePaymentWebhook` / `ParsePayoutWebhook`, return 2xx on success, otherwise the
  platform retries. Deduplicate deliveries by `eventId` and make order-state updates
  idempotent by `orderNo` or `merchantOrderNo`.

## Money safety

An order's state comes only from a query or a webhook, never from the kind of error a
create call returned. Three invariants hold in every row below:

- **`merchantOrderNo` never changes** during recovery.
- **`ORDER_NOT_FOUND` is not proof that nothing was created** once a request may have left
  your process: the platform can still be processing it, and a later query can find it.
- **A failed query is not a failed transaction.** On a timeout, connection failure or
  unparsable response, leave the order as it is and query again later.

### How the SDK reports an outcome

| Outcome | Go | JS / Python | PHP | Java |
|---|---|---|---|---|
| request error (nothing sent) | `ErrInvalidRequest` | `RequestError` | `RequestException` | `JoogopayException.Request` |
| transport error | `ErrTransport` | `TransportError` | `TransportException` | `JoogopayException.Transport` |
| non-envelope response | `ResponseError` | `ResponseError` | `ResponseException` | `JoogopayException.Response` |
| oversized response | `ErrResponseTooLarge` | `ResponseTooLargeError` | `ResponseTooLargeException` | `JoogopayException.ResponseTooLarge` |
| envelope business error | `APIError` | `APIError` | `ApiException` | `JoogopayException.Api` |

In Go: `errors.Is(err, joogopay.ErrInvalidRequest)`, `errors.Is(err, joogopay.ErrTransport)`,
`errors.As(err, &respErr)` for `*ResponseError`, `joogopay.AsAPIError(err)` for the envelope error;
the other languages throw the classes above.

### Recovery after a create call returned an error

| Situation | Could this attempt have created an order? | Query first | Resend same `merchantOrderNo` | Mark failed or refund on this alone |
|---|---|---|---|---|
| SDK request error: local validation failed, nothing was sent | no | no | yes, after fixing the request | first attempt only |
| Transport error (timeout, dropped connection), non-envelope or oversized response | yes | yes | yes, same parameters | never |
| envelope `msg` `IDEMPOTENCY_CONFLICT` | yes | yes | no, the number is taken | never |
| envelope `msg` `CHANNEL_ERROR` | yes | yes | only after a query returns `ORDER_NOT_FOUND` | only from a `FAILED` query result or webhook |
| envelope `msg` `CHANNEL_BUSY` | no | no | yes, after a short back-off | never |
| envelope `msg` `INVALID_FIELD`, `UNSUPPORTED_CURRENCY`, `UNSUPPORTED_METHOD`, `METHOD_NOT_ENABLED`, `INSUFFICIENT_BALANCE`, `ORDER_REJECTED`, `UNAUTHORIZED` or `RATE_LIMITED` | no | no | yes, after fixing the cause | never |
| any other envelope `msg`: `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE`, an empty `msg`, or one this table does not list | yes | yes | only after a query returns `ORDER_NOT_FOUND` | never |

- **SDK request error: local validation failed, nothing was sent**: Fix the request and resend the same `merchantOrderNo`. Marking it failed is safe only when no earlier attempt for this `merchantOrderNo` left the process; otherwise that earlier attempt is still unknown and must be queried.
- **Transport error (timeout, dropped connection), non-envelope or oversized response**: Outcome unknown: the platform may still be processing the request. Query the same `merchantOrderNo`; `ORDER_NOT_FOUND` means not found *yet*, not that nothing was created. Keep querying, or resend the same `merchantOrderNo` with the same parameters: the platform returns the existing order or `IDEMPOTENCY_CONFLICT`. Never mark failed, refund or change the number on this evidence.
- **envelope `msg` `IDEMPOTENCY_CONFLICT`**: The `merchantOrderNo` is taken but the platform could not return its order. Keep querying that number. Not found yet does not undo the conflict: do not mark failed, refund or allocate a new number.
- **envelope `msg` `CHANNEL_ERROR`**: The order may already exist. Query the original `merchantOrderNo` or wait for the `FAILED` webhook; only after the query returns `ORDER_NOT_FOUND` may the same number be sent again.
- **envelope `msg` `CHANNEL_BUSY`**: Refused before the order was created. Back off, then resend the same `merchantOrderNo`; no query is needed for this attempt. It says nothing about earlier attempts that are still unknown.
- **envelope `msg` `INVALID_FIELD`, `UNSUPPORTED_CURRENCY`, `UNSUPPORTED_METHOD`, `METHOD_NOT_ENABLED`, `INSUFFICIENT_BALANCE`, `ORDER_REJECTED`, `UNAUTHORIZED` or `RATE_LIMITED`**: The gateway refused the call before creating an order. Fix the cause and resend the same `merchantOrderNo`; if an earlier attempt for that number is still unknown, query it first. An order's failure comes from a query or a webhook, never from the error alone.
- **any other envelope `msg`: `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE`, an empty `msg`, or one this table does not list**: The order may exist. A 5xx, an empty `msg` and an unrecognised `msg` all say nothing about whether it was created, and a non-2xx HTTP response whose body still parses as an envelope arrives here too. Query the original `merchantOrderNo` and resend it only after the query returns `ORDER_NOT_FOUND`; resending changed parameters under a number that already exists returns the original order and silently drops the change.

Treating a request error like an unknown outcome leaves a payout in processing forever,
waiting for an upstream order that never existed; treating an unknown outcome or a
business error like a request error is how a payout gets sent twice or refunded while
the original request goes on to succeed.
